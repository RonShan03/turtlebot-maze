# Remote access preparation (manual; no machine changes performed)

The workstation runs Windows with Ubuntu WSL2 and Docker Desktop. Prefer Tailscale plus Windows Remote Desktop for this machine if its Windows edition supports hosting RDP; use ordinary Windows OpenSSH over Tailscale when a shell is sufficient. Tailscale's integrated SSH **server** targets supported Linux/macOS hosts, so `tailscale up --ssh` is not the Windows-host setup. A future Linux Docker workstation can use Tailscale SSH directly.

These are instructions for the owner to review and perform. This project does not install Tailscale/OpenSSH, enable unattended access, change firewall/power policies, open router ports, or enable RDP.

1. Install the official [Windows Tailscale client](https://tailscale.com/docs/install/windows) on the workstation and travel laptop, sign into the same account with MFA, and verify device approval in your admin console. Restrict tailnet access to your own identity and the selected machine. Do not enable Funnel, subnet routing or an exit node for this task.
2. On both machines run `tailscale status`; on the workstation run `tailscale ip -4`. From the travel laptop run `tailscale ping WORKSTATION_NAME`. Record the machine name and 100.x address in a private note, not Git. Do not commit reusable auth keys or account tokens.
3. For a GUI, review [Tailscale's Windows RDP procedure](https://tailscale.com/docs/solutions/access-remote-desktops-using-windows-rdp). Check Windows Settings → System → About for an edition with RDP hosting, then explicitly enable Remote Desktop and keep Network Level Authentication enabled. Restrict any approved inbound rule to your tailnet source addresses/interface; do not permit broad public-profile access. Connect using `mstsc /v:WORKSTATION_TAILSCALE_IP`. Windows login credentials still apply. Never forward TCP 3389 on the router.
4. For a shell, explicitly install/enable Microsoft's OpenSSH Server only if wanted. Use an SSH key and verify the host-key fingerprint locally; connect as `ssh WINDOWS_USER@WORKSTATION_TAILSCALE_IP`. Restrict any approved SSH rule to the tailnet. Do not open TCP 22 to the Internet and do not expose Docker's unauthenticated TCP API. Run Docker through the logged-in user's named pipe.
5. For a supported Linux host, review [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh), enable it explicitly, restrict the SSH access policy to your identity and non-root user, then verify `tailscale ssh USER@HOST`. Docker group membership grants powerful host access; use only your own controlled host.
6. Test over a phone hotspot: connect, run `docker info`, `docker compose -f assignments/assignment-3/compose.yaml --profile integration ps`, and execute the saved ROS smoke command. Lock the workstation and test again. If you choose unattended Tailscale service operation, sleep prevention or startup changes, approve and configure them yourself; Docker Desktop/WSL may still require user login after reboot. A powered-off or sleeping PC cannot be recovered through this tunnel alone.
7. Retrieve results with your chosen secure file transfer or Git (small approved artifacts). Retest after any network or Windows update. To revoke access, remove the travel device/keys from your tailnet and stop the approved remote service.

No public TCP services are required by the project's Compose file. All ROS nodes share one container and sensor/TF checks run through `docker compose exec`, which also avoids Windows-to-Linux DDS discovery complications. On a remote Linux VM, clone the authorized branch, build/import images and run the same headless commands. Use SSH port forwarding only if you later add a private web viewer.
